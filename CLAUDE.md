# CLAUDE.md — Credit Card Default Model

Guidance for Claude Code working in this repo. Read it before touching
any file.

## Purpose

A supervised-learning project that predicts which credit card clients
default next month (`default payment next month`, binary, ~22%
positive) on the UCI "Default of Credit Card Clients" dataset. It is
meant to show sound applied-ML practice: leakage-safe preprocessing,
validation that matches the data, metric choice suited to an imbalanced
target, and an explicit, defensible decision rule — not just a model
that runs.

**No overclaiming.** Nothing in this repo should describe capability
or results it doesn't actually have. If a metric hasn't been run
against real data, don't write a number for it — say "pending" or
leave a `TODO`. README numbers are generated from `artifacts/*.json`,
never typed by hand.

## Design principles

- **One split, one place.** `data.py` owns the train/test split. The
  test set is used once, for the final evaluation; it never informs
  model choice, tuning or threshold selection.
- **Everything learned from data lives inside the `Pipeline`.**
  Preprocessing (scaling, one-hot encoding) is fit on training data only.
- **Categorical codes are not ordinal.** `SEX`, `EDUCATION`,
  `MARRIAGE` are one-hot encoded.
- **Imbalance-aware selection.** Models are compared on cross-validated
  average precision, not accuracy.
- **Explicit operating point.** The deployed threshold maximises recall
  subject to a precision floor (`min_precision` in config), tuned on
  out-of-fold training predictions. If the floor is unattainable the
  code raises; it never falls back to a default threshold.
- **One evaluation code path.** Every model (main, baseline, comparison
  candidates) goes through `train.run_model`, so one model's metrics
  cannot be reported under another's name.

**Hard rule:** no module outside `data.py` may call `train_test_split`,
and no code outside the `Pipeline` object may call `.fit()` or
`.fit_transform()` on anything — in particular, never call
`fit_transform` on `X_test`. If you're tempted to scale data by hand in
a script, that's the signal the pipeline abstraction is being
bypassed — extend the pipeline instead. `tests/test_hard_rules_and_cli.py`
enforces this by scanning `src/`.

## Layout

```
credit-card-default-model/
├── CLAUDE.md                  this file
├── README.md                  problem, metric rationale, results, limitations, how to run
├── config.yaml                all run parameters — no hardcoded hyperparameters in code
├── pyproject.toml / requirements.txt
├── data/raw/                  default of credit card clients.xls goes here (gitignored)
├── notebooks/
│   └── 01_eda_and_experiments.ipynb   EDA + model-comparison narrative ONLY — never the source of the shipped model
├── src/credit_default/
│   ├── data.py                load_raw() + validation, split() — the ONLY place the split happens
│   ├── features.py            build_preprocessor() — scale numeric, one-hot categorical
│   ├── pipeline.py            build_pipeline() — preprocess → classifier, one sklearn Pipeline
│   ├── train.py               CLI: cross-validate → tune threshold → fit → evaluate once → persist
│   ├── evaluate.py            recall-at-precision-floor threshold tuning + metrics
│   ├── compare.py             CLI: candidate models ranked by CV average precision
│   ├── sensitivity.py         CLI: main model at several precision floors
│   └── report.py              regenerates the README results block from artifacts
├── tests/                     pytest suite (see "Definition of done")
└── artifacts/                 model.joblib, metrics.json, comparison.json, sensitivity.json (generated, gitignored)
```

## Definition of done

- [x] `pytest tests/` passes, and specifically includes tests that:
  - prove the scaler is never fit on test data (fitted parameters equal
    the training statistics and differ from full-data statistics)
  - prove `SEX`/`EDUCATION`/`MARRIAGE` are one-hot expanded, not passed
    through as raw ordinals
  - prove the tuned threshold respects the configured precision floor
    (and that an unattainable floor raises)
  - prove reproducibility given a fixed `random_state`
- [x] `python -m credit_default.train --config config.yaml` runs
  end-to-end against the real data file and writes
  `artifacts/metrics.json` with real (not placeholder) numbers
- [x] README's metric numbers match the actual artifacts — they are
  generated by `python -m credit_default.report`, and a test fails if
  they drift (`report --check`)
- [x] README states the precision-floor assumption in plain language
- [x] A single evaluation code path (`run_model`) for all models

## Commands

```bash
pip install -e ".[dev]"             # add ".[notebook]" to run the notebook
python -m credit_default.train --config config.yaml
python -m credit_default.compare --config config.yaml
python -m credit_default.sensitivity --config config.yaml
python -m credit_default.report     # refresh README results block
pytest tests/ -v
```

## Style

- Type hints on all function signatures.
- Docstrings explain *why*, not just what.
- No bare `except:`. No silent fallbacks that mask a data problem.
- Keep `config.yaml` as the single place hyperparameters, paths, and
  the precision floor live; don't reintroduce magic numbers into `src/`.
- When behaviour changes, update the README and, if the numbers move,
  re-run the CLIs and `report` so they stay in step.
